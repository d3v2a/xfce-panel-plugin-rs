# Rust FFI audit of the xfce4-panel plugin API

In-depth analysis of the entry points, method signatures and C types of the
xfce4-panel plugin API ([xfce4-panel](https://gitlab.xfce.org/xfce/xfce4-panel)),
to assess what would be hard to handle in Rust.

**Overall verdict: feasible without modifying the panel. No blocking point
identified.** The recommended path: a Rust cdylib exporting
`xfce_panel_module_init` (the modern ABI), with a Rust GObject subtype of
`XfcePanelPlugin`. The legacy `_construct` path remains a valid, simpler
alternative for an initial spike.

## A. Entry points exported by the plugin

The panel (and the wrapper) probe **at most 3 symbols** (exhaustive
`grep g_module_symbol`: `panel/panel-module.c:210,221`, `wrapper/main.c:293`,
`wrapper/wrapper-module.c:137,151`):

| Symbol | Exact signature | Probed where | Status |
|---|---|---|---|
| `xfce_panel_module_preinit` | `gboolean (gint argc, gchar **argv)` | `wrapper/main.c:293` — before `gtk_init()` | optional; its presence on an internal plugin **forces external mode** (`panel/panel-module.c:189-207`) → to avoid in v1 |
| `xfce_panel_module_init` | `GType (GTypeModule *type_module, gboolean *make_resident)` — typedef `PluginInitFunc`, `libxfce4panel/xfce-panel-plugin-provider.h:37-39`; generated by `_XPP_DEFINE_PLUGIN` (`xfce-panel-macros.h:208-232`) | `panel-module.c:210`, `wrapper-module.c:137` (the wrapper passes `make_resident=NULL`) | **modern ABI — recommended path** |
| `xfce_panel_module_construct` | `XfcePanelPlugin * (const gchar *name, gint unique_id, const gchar *display_name, const gchar *comment, gchar **arguments, GdkScreen *screen)` — typedef `PluginConstructFunc`, `provider.h:31-38`; generated by `XFCE_PANEL_PLUGIN_REGISTER` (`xfce-panel-macros.h:327-368`) | `panel-module.c:221` (fallback if `_init` is absent), `wrapper-module.c:151` | legacy (4.6 compat) — a good spike path: **less machinery** (no GTypeModule); drawback: internal construct-func plugins are **always resident** (`panel-module.c:229`) |

Behaviour of the legacy macro on the C side (important for the Rust port):
`XFCE_PANEL_PLUGIN_REGISTER` itself creates
`g_object_new(XFCE_TYPE_PANEL_PLUGIN, "name", …, "unique-id", …, NULL)` and hooks
the user callback onto the `realize` signal (`connect_after`, macros.h:367-368).
**In Rust we do not reuse the macro**: we write the exported function ourselves,
which creates an instance of our GObject subtype and returns the pointer — the
panel performs **no type check** on the returned object (`G_IS_XFCE_PANEL_PLUGIN`
absent; a behavioural contract only: the type must descend from
`XfcePanelPlugin`, else a critical + silent segfault). A Rust subtype is therefore
accepted on both paths.

## C. The `XfcePanelPluginProvider` interface (`provider.h:40-75`)

A GObject interface (parent) implemented by `XfcePanelPlugin`
(`xfce-panel-plugin.c:245-248`, slot mapping ~L700-720). **This is what the panel
calls** — never the direct vtable.

18 slots: `get_name → gchar*`, `get_unique_id → gint`, `hidden_event`,
`set_size(gint)`, `set_icon_size(gint)`, `set_dark_mode(gboolean)`,
`set_mode(XfcePanelPluginMode)`, `set_nrows(guint)`,
`set_screen_position(XfceScreenPosition)`, `save`, `get_show_configure → gboolean`,
`show_configure`, `get_show_about → gboolean`, `show_about`, `removed`,
`remote_event(name, const GValue*, guint *handle) → gboolean`, `set_locked(gboolean)`,
`ask_remove`.

+ 18 wrapper functions `xfce_panel_plugin_provider_*` (`provider.h:~179-246`) +
the upward signal **`provider-signal`** (UINT, defined `provider.c:34-42`) with
the `XfcePanelPluginProviderSignal` enum of 18 values (`provider.h:78-98`).

On the Rust side: the slots are inherited/implemented by the C base class (the
subtype has nothing to do there); the wrapper functions are called **by the
panel**, not by the plugin. The only thing to note is that the panel's external
widget (`PanelPluginExternalWrapper`) relays D-Bus → these functions: no extra
work on the plugin side in external mode.

## D. `XfcePanelPlugin`'s GObject signals (class_init, `xfce-panel-plugin.c:249+`)

All `RUN_LAST`, wired to the vtable slots of §B:
`about()`, `configure-plugin()`, `free-data()`, `hidden-event(gboolean)`,
`orientation-changed(GtkOrientation)`, `mode-changed(XfcePanelPluginMode)`,
`nrows-changed(guint)`, **`remote-event(string, GValue) → gboolean`** [custom
marshaller `BOOLEAN:STRING,BOXED`], `removed()`, `save()`,
**`size-changed(int) → gboolean`** [custom `BOOLEAN__INT`, accumulator
"true_handled"], `screen-position-changed(XfceScreenPosition)`.

**Construct-only** properties: `name`, `display-name`, `comment`, `unique-id`,
`arguments` (boxed STRV). → when creating the Rust instance via `g_object_new`,
you must supply `arguments` as a boxed STRV GValue built from the received
`char**` (see §F, "medium").

## E. Post-instantiation execution contract (internal mode)

The exact sequence the plugin undergoes after insertion
(`panel/panel-window.c:4293-4331`):
1. `g_module_open(filename, G_MODULE_BIND_LOCAL)` (`panel-module.c:180`);
2. load → `_init_func(type_module, &make_resident=TRUE)`, `g_module_make_resident` if requested (~L210-215);
3. `new_plugin`: `g_type_module_use()` + `g_object_new(plugin_type, "name", …, "arguments", NULL)` — **no screen parameter** on the init path (`panel-module.c:405-485`, `g_object_new` ~:431); weak-ref + qdata set by the panel;
4. insertion: connect the `provider-signal` signal → `itembar_insert` → if the window is realized, `set_provider_info`, else an idle `set_all_provider_info` (`panel-window.c:2152` / 2119-2127);
5. **provider sequence**: `set_locked` → `set_mode` → `set_screen_position` → `set_size` → `set_icon_size` (→ triggers `set_size -1`) → `set_dark_mode` → `set_nrows` (→ `set_size -1`);
6. save: `provider_save` on each child (`panel-application.c:1420`);
7. removal: `PROVIDER_SIGNAL_REMOVE_PLUGIN` → `provider_removed()` → `container_remove` → dispose → `free-data`.

Practical consequence: the Rust subtype must **tolerate these calls before/after
realize** in any order, and `size_changed(-1)` means "automatic size".

## F. C types of the signatures → Rust-side complexity

| Type | Definition | Rust complexity | Rationale / memory conventions |
|---|---|---|---|
| `gchar *` (name/display/comment) | glib | **Easy** | read-only, owned by the panel; const getters, **nothing to free** |
| `gchar ** arguments` | glib STRV | **Medium** | official doc: "should not be freed" (`xfce-panel-plugin.c:1888`) — convert into a boxed STRV GValue for the `g_object_new`, no freeing |
| `GValue *` (remote_event) | gobject, opaque | **Medium → hard** | arbitrary contained type (e.g. D-Bus deserialization via `g_dbus_gvariant_to_gvalue`, `panel-dbus-service.c:291`); **returning FALSE is acceptable in v1** — the only real hard point of the whole API surface |
| `GdkScreen *` | gtk3 | **Easy** | provided by gtk-rs (legacy path only) |
| `GtkAllocation`, `GParamSpec` | gtk/gobject | **Easy** | gtk-rs / glib-rs native |
| enums `XfcePanelPluginMode`(3), `XfceScreenPosition`(17) | `libxfce4panel-enums.h:50-100` | **Easy** | simple C enums → `#[repr(C)]` Rust (caution: the **anonymous** enums of provider.h:133-156 — `PLUGIN_EXIT_*` and `PLUGIN_ARGV_*` — are a bindgen weak spot, to define by hand) |
| `cairo_t` / surfaces | cairo | **Manageable** | cairo-rs native if custom drawing is needed |
| returns allocated to the plugin | — | **Easy** | only `lookup_rc_file()`/`save_location()` are "transfer full" (g_free on the plugin side) |

General convention: the panel passes only non-freeable pointers to the vtable;
the only outgoing allocations from the panel to the plugin are the 2 rc-file
functions above.

## G. Typical plugin dependencies & config persistence

On `clock`/`separator` (both meson.build): gtk, cairo, **libxfce4util**,
libxfce4ui, libxfce4windowing, **xfconf**, link `libpanel_common` +
`libxfce4panel`.

Config persistence: plugins do not use raw `xfce_conf_*` — the panel goes through
an internal helper `panel_properties_bind(XfconfChannel*, GObject*, const gchar
*property_base /* "/plugins/plugin-%d" */, PanelProperty[] {name, GType},
gboolean save)` (`common/panel-xfconf.c:59-130`) = `xfconf_init` +
`xfconf_channel_get(XFCE_PANEL_CHANNEL_NAME)` + `xfconf_g_property_bind`. **On the
Rust side: implemented** in `crates/xfce-panel/src/settings.rs`
(`xfce_panel::Channel`) over the `xfconf` crate (0.3, xfce4-rs) —
`Channel::new(plugin)` uses `xfce_panel_get_channel_name()` +
`plugin.property_base()`; the `#[panel_settings]` attribute generates the
`ParamSpec` + the xfconf type of each field and `Settings::bind_to(channel)`
replays the `PanelProperty[]` loop (binding + seeding the default). A pitfall
verified on the sources: `REAL_PROP` (`xfconf-channel.c:44`) concatenates base +
property **without a separator** → the path passed to `bind` must be **relative to
the base with a leading `/`** (`"/shout"` → `/plugins/plugin-<id>/shout`, the base
keyed on the unique id, not the name: `common/panel-private.h:83`);
`xfconf-binding.c:549` rejects any path without a leading `/`. A runtime pitfall
verified by test (`crates/xfce-panel-demo/tests/settings_e2e.rs`): deleting the
bound xfconf key reloads the **`ParamSpec` default** (`xfconf-binding.c:376`),
`NULL` for a string → the bound property must be `Option<String>`, else the
derived setter panics in the panel process. The binding never creates the key:
`Channel::ensure` seeds the default (the equivalent of `panel_properties_bind`'s
`save=TRUE`). A runtime pitfall verified by test: binding the settings-dialog
widgets **to the settings object** `BIDIRECTIONAL` does the reverse of the xfconf
binding — `g_object_bind_property` copies the *target's initial value into the
source*, so fresh widgets overwrite the loaded settings at `bind` time;
`channel.bind(path, type, &widget, "text")` on the contrary loads the saved value
into the widget, and the binding dies with it (`xfconf-binding.c:456`,
`g_object_weak_ref` on the target). A dependency-free alternative: rc-file via
`save_location()`.

The `.desktop` keys read by the panel (`panel-module.c:322-384`) and affecting
runtime: `X-XFCE-API == "2.0"` **mandatory**, `X-XFCE-Module`,
`X-XFCE-Internal=TRUE`, `Name`, `Comment`, `Icon`, `X-XFCE-Unique`.

## H. bindgen verdict

**Yes, feasible.** The public headers (`libxfce4panel/*.h`) include only
`gtk/gtk.h` + `glib(-object).h` (no cairo), and contain neither inline functions
nor unions. Conditions:
1. **define `_LIBXFCE4PANEL_INSIDE_LIBXFCE4PANEL_H`** (`-D` clang) — an `#error` guard in each header (e.g. `xfce-panel-plugin.h:20-22`);
2. the `libxfce4panel-enums.h` header is **generated at build by glib-mkenums** and absent from the tree → parse only `xfce-panel-plugin.h` + `xfce-panel-plugin-provider.h`, enums by hand;
3. **blocklist the gtk/glib types** (provided by gtk-rs/glib-rs) — generate only the function externs + the 2 public enums;
4. the **anonymous** enums (`provider.h:133-143` `PLUGIN_EXIT_*`, :146-156 `PLUGIN_ARGV_*`) = bindgen weak spot → define by hand in Rust;
5. **the `libxfce4util` sources are vendored in the repo** (19 public headers): the Xfce include chain (libxfce4panel → libxfce4util) is thus version-pinned without depending on the system's -dev packages; only gtk/glib come from the system. Bonus: the C implementations stay readable as a Rust-porting reference (popup helpers, rc-file, toplevel…);
6. **the official `xfce4-rs` workspace exists** (gitlab.xfce.org/bindings/xfce4-rs, v0.3.0+dev): its sys crates are NOT generated by bindgen but by the **gir** codegen (gtk-rs/gir submodule + `Gir.toml`), with build.rs = a simple `system-deps` probe. Two options for our panel-sys crate: direct bindgen (§H above, simpler) or the official workspace's gir recipe/conventions → **upstreaming of `libxfce4panel` is possible** (an explicit "TODO" in their roadmap; only gtk3-rs 0.19 / glib 0.22 / MSRV rust 1.92 to align).

For `XfcePanelPlugin` itself: do not re-generate the GObject type — a 100% manual
path (`GTypeInfo` + class_init over the repr-C class struct, parent =
`xfce_panel_plugin_get_type()` as the only extern), see §I; automatic
gtk-rs/glib-rs subclassing is excluded (double type registration).

## I. The GTypeModule path in Rust — what concretely to implement

**False question: no need for a "Rust type of GTypeModule".** The module instance
is owned and created by the panel (C subclass `PanelModule`) via
`g_type_module_use()`; our exported function **receives** the pointer. We never
build or sub-class this type in Rust:

```
panel:    g_type_module_use(PanelModule) → load() → g_module_open(.so)
          → our xfce_panel_module_init(type_module, &make_resident)
              1. dynamic registration of OUR GObject type (§I.1)
              2. *make_resident = FALSE   (like clock; caution: the wrapper passes NULL!)
              3. return MY_PLUGIN_TYPE    (GType of the Rust subtype)
```

### I.1 The dynamic GObject type registration (the real piece to write)

A Rust port of what the C macros `XFCE_PANEL_DEFINE_TYPE` / `_XPP_DEFINE_PLUGIN` do:

1. **A repr(C) `GTypeInfo` struct** (standard GLib API): `{ class_size,
   instance_size, g_base_init, class_init, instance_init, interfaces }`, stored in
   a **static** — GLib requires its persistence (it makes no copy).
2. **`class_init`**: cast `parent_class` to `XfcePanelPluginClass*` and fill the
   ~13 vtable slots of §B (Rust trampolines). No custom property to install:
   `name`, `unique-id`, … come from the base class.
3. **`instance_init`**: empty — the plugin state lives in **GData on the object**
   (the `private_data` pattern of rofi-mode.rs), so
   `instance_size = sizeof(XfcePanelPlugin)` and
   `class_size = sizeof(XfcePanelPluginClass)` → **no memory-layout extension**.
4. A single call: `g_type_module_register_type(module, XFCE_TYPE_PANEL_PLUGIN,
   "XfceMyPlugin", &INFO, 0)` — the module **unregisters** the type at the last
   `g_type_module_unuse()`; the panel destroys instances before the unuse (§E) →
   no dangling. Re-use after unuse: re-registrable without issue (persistent
   static + name freed at unuse), identical behaviour to C plugins.

**Why NOT to use automatic gtk-rs/glib-rs subclassing**: it would register the
type globally at the first `get_type()` → double registration with the module →
GLib assert "type already exists". Hence the 100% manual path (raw structs + FFI),
which is the planned path anyway; the safe helpers of the higher crate are written
on top.

### I.2 Complexity verdict & known pitfalls

**Complexity: moderate and well understood — ~60-100 lines of FFI once, in the
sys crate.** Absorbed by the existing implementation estimate: no change to the
overall effort. What changes is the spike strategy (direct init path).

Identified pitfalls:
- **`make_resident` may be NULL** — the wrapper passes `NULL`
  (`wrapper/wrapper-module.c:137`) → guard before writing;
- **`GTypeInfo` must survive the whole life of the type** → static, bare function
  pointers in class_init/instance_init (no closures);
- `make_resident = FALSE` by default (like clock, `XFCE_PANEL_DEFINE_PLUGIN`): the
  module can be closed when no longer used — the `.so`'s Rust code is unloaded and
  re-initializable; `TRUE` = permanently resident.

## J. Potential Rust-side complications, ranked

**Blocking: none.**

**Mitigated:**
1. **Static `GTypeInfo` + `g_type_module_register_type` from Rust** — detailed and
   judged feasible in [§I](#i-the-gtypemodule-path-in-rust--what-concretely-to-implement):
   ~60-100 lines of FFI once. This is the entry point of the init path (chosen as
   the direct target, no legacy spike).
2. **Manual filling of the `XfcePanelPluginClass` vtable** (repr C + trampolines)
   — limited volume (§B: ~13 members), the same pattern as rofi-mode.rs's
   trampolines.
3. **The boxed STRV `arguments` property** at construction — `char** → GValue`
   glib conversion, ~20 lines.
4. **No type-check on the panel side** = silent crash on bad GObject parenting →
   plan a test harness that loads the cdylib through the real panel (not only unit
   tests).
5. **`remote_event(GValue*)`** — return FALSE in v1; later implement the events
   actually emitted by the panel (lists in the `XfcePanelPluginProviderSignal` enum).

**Manageable:** string ownership (nothing to free), enums, i18n
(`xfce_textdomain`), dialogs via `gtk::Builder` + GResource (replacing
`panel_utils_builder_new`), cairo drawing, xfconf binding (~50 lines) or rc-file.
**The external/wrapper mode (D-Bus + GtkPlug) remains the escape hatch** if the
cdylib ran into trouble with `G_MODULE_BIND_LOCAL`.

## K. Target use case: a "calendar-type" plugin — display, popup and settings

Audit of the clock plugin (`plugins/clock/{clock.c,clock.h}`) to answer:
*can we display anything, or is GTK forced?* + how the panel handles display and
settings.

### K.1 In the bar: **GTK is forced**, but the content is free

- **The plugin IS the EventBox**: `XfcePanelPlugin` is a subtype of
  `GtkEventBox` (`xfce-panel-plugin.c:245`) with `visible-window = FALSE`
  (line 780, "hide the event box window to make the plugin transparent") → no
  GdkWindow of its own → fully transparent; the background/borders are drawn by
  `PanelBaseWindow` in CSS and show through.
- In `construct`, we do `gtk_container_add(plugin, <its single child>)` — it is a
  **GtkBin**: exactly ONE widget (in practice plugins add a `GtkBox` there holding
  the rest, e.g. launcher.c:367). Anything GTK/Cairo passes (composite widgets,
  `GtkDrawingArea` with free drawing…).
- `construct` is invoked **at the plugin's realize**
  (`xfce_panel_plugin_realize`, lines 1018-1038), not at GObject construction — the
  children are added there then realized by GTK. A useful detail for the Rust slot
  mapping.
- Event flow: **windowed** children (e.g. `GtkButton`) receive their events
  directly; non-windowed areas and anything unconsumed bubble up — XfcePanelPlugin's
  `button_press_event` override (`:269`, impl. `:1042-1083`) intercepts right-click
  / Ctrl+left-click for the **plugin's context menu**, returns FALSE otherwise; the
  rest (moving the bar, panel menu) is handled by PanelWindow
  (`panel-window.c:1362-1435`). No enter/leave/motion handler on the panel side.
- CSS: the EventBox gets the `.panel-plugin` + `<name>` classes and the node name
  `<name>-<id>` (lines 921-937) → per-plugin theming is possible.
- Dimensional constraint: **only the length along the bar is negotiable**; the
  thickness and borders are imposed by the itembar's allocation distribution
  (`panel/panel-itembar.c`, `size_allocate` :487+). That is why the clock overrides
  `get_request_mode` to expose only the length (`clock.c:646-654`).
- Another toolkit (Qt, a webview in a separate window) cannot live *inside* the
  bar; a popup gets around this limit since it leaves the bar (K.2).

### K.2 Calendar popup: **GTK not forced — and not even libxfce4ui**

Contrary to intuition, the clock's calendar uses **no libxfce4ui/`XfceCalendar`
widget** (`grep Xfc = 0 occurrence in plugins/clock`):
- It is a TOPLEVEL `GtkWindow` containing a pure `GtkCalendar` (function
  `clock_plugin_popup_calendar`, clock.c:1377+).
- Positioning/decoration/attachment is handled by the **libxfce4panel** helper
  `xfce_panel_plugin_popup_window()` (`xfce-panel-plugin.c:3043-3125`): utility
  hints, undecorated window, keep-above, placement relative to the widget
  (top/left), Wayland layer attachment TOP+LEFT, automatic close (Esc / outside
  click / focus loss), blocking the panel's autohide while shown.
- The content is **entirely free**: it is the plugin that builds the window
  (`clock_plugin_popup_calendar`), it can put any GTK widget there (or a
  `GtkDrawingArea`). The helper is a convenience, not a constraint — you can also
  create your own `GtkWindow` and handle placement/focus yourself (which is exactly
  what the wrapper does: `wrapper-popup.c` for internal modules).
- Bonus: the clock's **`command`** property (`clock.c:504`) — if non-empty, the
  click launches an **external command** instead of opening the calendar. A plugin
  can therefore delegate its whole UI to a third-party process (a task manager,
  say).
- Note: no `day-selected` handler in the clock → date selection has no action
  (display only).

### K.3 Settings: a simple mechanism, 100% under the plugin's control

**Showing the "Configure…" menu entry**:
1. Fill the `configure_plugin(GtkWidget*)` vtable;
2. **Explicitly call `xfce_panel_plugin_menu_show_configure()` in the construction
   callback** — the panel does NOT derive this flag from the vtable (negative
   proof: no `if (class->configure_plugin) flag`, `xfce-panel-plugin.c:1645-1652`);
   it is the clock's call (`clock.c:547`) that sets it. Forgetting it = the
   "Configure…" entry absent, no error;
3. The panel then handles everything: position (context menu or action-bar),
   acceleration, the plugins' secondary menu (action `PanelPluginConfigure`,
   `xfce-panel-plugin.c:1560-1568`).

**The dialog itself**: entirely free — the clock uses `XfceTitledDialog` +
GtkBuilder from a GResource (`/org/xfce/panel/clock-dialog.glade`) but that is an
internal choice; any `GtkDialog` suffices. The plugin receives the panel's widget
(hence theme access via GtkSettings) and handles closing itself.

**Persisting values**: bidirectional **xfconf** binding under
`/plugins/plugin-N` (channel `xfce4-panel`) via the `panel_properties_bind` pattern
(`clock.c:525-556`: a `PanelProperty[]` table + binding calls in
`clock_plugin_construct`). The panel creates/frames the sub-key by plugin number;
the plugin only handles the bindings. No `save()` callback to write — reading at
load and writing at close are automatic. **On the Rust side, zero FFI**: the
`xfconf` crate (xfce4-rs workspace) provides
`Channel::with_property_base("xfce4-panel", plugin)` +
`bind_property(path, glib::Type, object, prop)` which directly wraps
`xfconf_g_property_bind`.

**Verdict**: for a calendar plugin, everything is doable without any surprising
constraint — GTK forced only *inside* the bar (as expected), popup free in content
(even an external process), settings = 1 vtable slot + 1 call in construct + xfconf
bindings.

### K.4 Context menu: entries provided by the panel, dialogs to implement yourself

The right-click/Ctrl+left menu is built by **libxfce4panel**
(`xfce_panel_plugin_menu_get`, `:1209-1389`), not by the plugin — but with a clear
division of labour:

| Entry | Display condition | Dialog |
|---|---|---|
| Header (name) + custom items (`menu_insert_item`) | always / if added | n/a |
| **Properties** | `PLUGIN_FLAG_SHOW_CONFIGURE` → called by **us** in construct (`xfce_panel_plugin_menu_show_configure()`, flag set at `:2304`) | emits the `configure-plugin` signal (**vtable slot `configure_plugin`**) → **dialog to implement** (K.3) |
| **About** | `PLUGIN_FLAG_SHOW_ABOUT` → called by **us** in construct (`xfce_panel_plugin_menu_show_about()`, flag set at `:2339`) | emits the `about` signal (**vtable slot `about`**, `xfce-panel-plugin.h:~127`) → **dialog to implement, NO generic dialog** in this tree |
| Move / Remove | if the panel is not locked | handled by the panel (confirm + provider) |
| "Panel…" sub-menu (add items, prefs, logout, help, panel About) | always | handled by the panel (provider signals); the *panel's* About is the only `GtkAboutDialog` in the tree (`panel-dialogs.c:63-92`) |

Key points for About:
- The panel does store plugin data — `display-name`/`comment` read from the
  **`.desktop`** (`panel-module.c:378-435`) and exposed as GObject props — but it
  uses them only for the menu header and the Remove text. The `.desktop`
  website/authors fields are **not** read.
- So: for an About, we fill the `about` vtable slot (or connect the `"about"`
  signal) and show our own `GtkAboutDialog` (version/website/authors as compile-time
  constants + display-name/comment from the plugin's props). Forgetting the
  `menu_show_about()` call in construct = entry absent, no error.
- None of the shipped plugins implements `about` (empty grep) → in practice the
  entry appears there only if the plugin opts in.

**Rust-side cost**: one more optional vtable slot (`about`, the same trampoline
pattern as `configure_plugin`) — ~20 lines with a `gtk::AboutDialog`.

## Conclusion

Writing an xfce4-panel plugin in Rust is feasible without touching the panel
binary. Target architecture: a cdylib exporting `xfce_panel_module_init` + a Rust
GObject subtype of `XfcePanelPlugin` (gsub subclass + targeted externs + manual
vtable) + a `.desktop` with `X-XFCE-Internal=TRUE` / `X-XFCE-API=2.0` + config via
xfconf (`xfce4-panel`, `/plugins/plugin-N`) or rc-file. Surface to implement: 1
exported function, ~13 vtable slots, 0 Provider slot (inherited from the base), and
the only genuinely hard type (`GValue*`) can be deferred in v1.
